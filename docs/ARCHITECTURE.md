# Техническая архитектура — исходный проект и целевое состояние
Версия: 0.1 · 19.11.2026

## Фактическое состояние на начало работы
- Ветка main: статический PWA-калькулятор на HTML, CSS, JavaScript, Preact/HTM. Исходные модули находятся в корне и js/. Формулы — js/calc.js, проверяются tests/calc.test.mjs.
- Ветка claude/busy-keller-aq3zrr: добавлен android-app/ с Capacitor 7 и GitHub Actions для APK. Скрипт android-app/scripts/copy-web.mjs копирует существующий сайт целиком в android-app/www. **Сейчас Android — оболочка сайта, а не отдельный интерфейс.**
- Данные сайта: localStorage + Firebase Firestore после входа; настройки хранятся в users/{uid}, заказы — users/{uid}/orders/{id}. Последние черновики расчётов локальные.
- Android-ветка не включена в main. Никаких миграций данных и смен package ID до согласованного выпуска.

## Целевое разделение
1. **Web Calculator** — нынешний сайт, внешне остаётся прежним.
2. **Shared Core** — чистые вычисления и схемы данных, не зависят от DOM, Capacitor, Firebase и интерфейса.
3. **Mobile App** — самостоятельный UI Android: главная, объекты, рабочая сессия, мастерская, прогресс. Оборачивается существующим Capacitor.
4. **Data Layer** — локальная база с надёжными транзакциями и очередь синхронизации с Firebase, после проверки технического решения.
5. **Cloud** — Firestore и, если согласуем фотографии, отдельное файловое хранилище с правилами доступа.

Возможная будущая структура (это направление, НЕ уже созданные каталоги):
    /                 — работающий сайт
    js/calc.js        — текущие расчёты до безопасного переноса
    /shared/          — общая предметная логика и схемы
    /mobile/          — новый интерфейс приложения
    /android-app/     — существующий Capacitor/Gradle проект
    /tests/           — тесты расчётов и доменной логики
    /docs/            — решения, схемы, сценарии и план

## Стратегия постепенного перехода
Этап А: не трогаем main; работаем в ветке от актуального Android-проекта.
Этап Б: проверяем сборку APK без изменения публичного сайта.
Этап В: добавляем независимую точку входа mobile/ и тестовый главный экран; меняем упаковку Capacitor так, чтобы брал mobile/ вместо корня сайта.
Этап Г: выделяем общую предметную логику из js/calc.js через тесты; НЕ копируем формулы в двух несвязанных версиях.
Этап Д: добавляем новую модель объектов, сессий, склада. Существующие заказы остаются читаемыми; миграции только после теста на копии данных и резервного сохранения.

## Критические архитектурные решения
- **Идентичности:** неизменяемые случайные UUID для новых сущностей. Старые ID заказов не переписывать.
- **История времени:** хранить события start/stage/pause/resume/finish с идентификаторами и датами, а итоговые минуты пересчитывать. Операции должны быть идемпотентными.
- **Учёт запасов:** отдельные проводки прихода, расхода, возврата и корректировки. Остаток вычислять из движений, а не безвозвратно перезаписывать число.
- **Цены:** денежные суммы в минимальных целых единицах валюты, без неявного смешения граммов, мл и литров; материал имеет базовую единицу учёта.
- **Историческая себестоимость:** фиксировать закупочную цену/оценку на момент списания, не менять прошлую прибыль при новом прайсе.
- **Синхронизация:** нельзя полагаться только на схему «последняя запись победила» для склада и рабочего времени. У событий отдельные ID, повторная отправка не создаёт дублей. Конфликты исправления сущностей выводить явно.
- **Долговечность:** localStorage недостаточен для больших каталогов, очереди событий и фотографий. Выбор локального хранилища (SQLite/IndexedDB + Capacitor-совместимость) сделать до реализации склада, с проверкой работы на Android.
- **Безопасность:** исключить ключи подписи и приватные токены из репозитория; проверять Firebase Security Rules для новых коллекций; резервное копирование и экспорт до миграций; не логировать персональные данные.
- **Нативные функции:** включать только по мере нужды (камера, выбор фото, файловая система, share, уведомления). Не запрашивать разрешения заранее.
- **Сборка:** отдельные debug/preview и подписанная стабильная версия; проверки Node перед Gradle; автоматический APK на ветках разработки; стабильное обновление только после проверки.
- **Не менять Android applicationId com.restoration.calc** без специального решения: иначе обновление установленного приложения потребует миграции/переустановки.

## Ограничения и текущие риски
- Уже существующие данные нужно сохранять; новая модель не должна ломать открытие старых заказов.
- GitHub Actions Android-проекта сейчас находится только в отдельной ветке, а не в main.
- В облаке уже существуют настройки/заказы; новые коллекции должны быть совместимы с существующими путями.
- Проверка логина Google, релизной подписи и установки APK на реальном телефоне обязательна перед стабильным выпуском.
- Нельзя считать расходы на инструмент, налоги и амортизацию учтёнными, если пользователь их не внёс.

## Точки принятия решений до активного программирования
1. Проверить фактический APK и процедуру обновления.
2. Выбрать долговременное локальное хранилище после прототипа и стресс-теста (offline/restart/multiple events).
3. Утвердить сквозную модель объектов и связать со старыми заказами.
4. Проверить правила безопасности Firebase и план резервной копии.
5. Только после этого включать реальные движения склада и учёт клиентских фотографий.
